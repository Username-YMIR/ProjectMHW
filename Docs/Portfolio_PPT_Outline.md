# ProjectMHW 발표 자료 초안

## 문서 목적
- 제공된 발표 메모와 `Docs` 문서를 바탕으로, 프로그래머 관점이 드러나는 포트폴리오형 발표 자료 초안을 정리한다.
- 추후 PPT 제작 시 바로 옮길 수 있도록 `목차 + 페이지 단위`로 구성한다.
- 기능 소개보다 `문제 정의 -> 설계 선택 -> 구현 방식 -> 트레이드오프 -> 개선안` 흐름이 보이도록 정리한다.

## 발표 전체 콘셉트
이 발표의 핵심 메시지는 아래 한 문장으로 잡는 것을 권장한다.

`데이터 정의, 장비 적용, 전투 계산, UI 표시를 분리해 액션 전투 시스템을 구조화한 경험`

## 권장 분량
- 메인 발표: 15페이지
- 부록: 2~3페이지 선택
- 발표 시간 기준:
  - 10분 발표면 12~13페이지
  - 15분 발표면 아래 15페이지 구성이 적절

## 목차
1. 프로젝트 소개
2. 기술 목표와 설계 방향
3. 전체 아키텍처 개요
4. 아이템 계층구조와 데이터 레지스트리
5. ItemInstance 자동 적용 구조
6. 장비 스탯의 GAS 반영 구조
7. 대미지 전달 파이프라인
8. 피격 결과 처리와 후속 액션
9. 공통 UI 설계와 스탯 반영
10. 대미지 텍스트 위젯/액터
11. 메인 메뉴 구조
12. 로딩 화면과 레벨 전환
13. 설계 강점
14. 한계와 개선안
15. 마무리

## Page 2. 기술 목표와 설계 방향
**슬라이드 제목**
`무엇을 해결하려 했는가`

**핵심 메시지**
- 데이터가 많아질수록 콘텐츠 관리 비용이 증가하고, 액션 전투는 수치 계산과 연출 타이밍이 엮이기 때문에 계층 분리가 필요했다.

**본문 포인트**
- 해결하려던 문제
  - 통합 DataTable은 아이템 종류별 불필요한 컬럼까지 함께 가진다.
  - 전투 수치와 무기 비주얼, UI 표기가 한곳에 뭉치면 수정 비용이 커진다.
  - 공격 시작 시점과 명중 시점이 달라질 수 있어 대미지 스냅샷 구조가 필요했다.
- 설계 방향
  - 콘텐츠 정의는 `ItemData`
  - 런타임 비주얼 적용은 `ItemInstance`
  - 장비 상태와 전투 수치는 `Player + GAS`
  - UI는 표시 전용으로 분리

**추천 시각 자료**
- 좌측 `문제`, 우측 `설계 원칙` 2단 구성

**발표 포인트**
- "핵심은 데이터 드리븐을 무조건 밀어붙이는 게 아니라, 액션 게임에서 실제로 유리한 책임 분리를 선택한 것입니다."

## Page 3. 전체 아키텍처 개요
**슬라이드 제목**
`데이터에서 UI까지의 전체 흐름`

**핵심 메시지**
- 아이템 데이터가 직접 게임을 움직이는 것이 아니라, 레이어를 거치며 런타임 상태로 변환되는 구조다.

**본문 포인트**
- 전체 흐름
  - `ItemDataRegistry`
  - `ItemInstance`
  - `PlayerCharacter`
  - `GameplayEffect / AttributeSet / Execution`
  - `Frontend UI / Ingame UI`
- 프론트와 인게임은 같은 데이터를 보되 참조 경로가 다르다.
- 전투 계산은 정적 데이터가 아니라 ASC의 현재값 기준으로 수행된다.

**추천 시각 자료**
- `Docs/ItemHierarchy_Reference_UML.md`의 레이어 구조도 사용

**발표 포인트**
- "이 슬라이드 하나로 발표 전체를 묶습니다. 뒤 슬라이드들은 이 흐름의 각 단계를 깊게 설명하는 방식입니다."

## Page 4. 아이템 계층구조와 데이터 레지스트리
**슬라이드 제목**
`DataTable 대신 Registry + Instanced UObject`

**핵심 메시지**
- 아이템 종류별로 불필요한 필드를 함께 들고 다니는 구조를 피하기 위해, 계층형 `ItemData`와 `Registry` 조합을 선택했다.

**본문 포인트**
- 설계 이유
  - 통합 DT는 무기/방어구/소비 아이템이 같은 스키마를 강제로 공유한다.
  - 아이템 종류가 늘수록 컬럼과 예외가 많아진다.
- 선택한 방식
  - `UItemDataRegistry`
  - `TMap<FName, UMHItemDataBase*>`
  - `Instanced UObject ItemData`
- 왜 `TMap<FName>`인가
  - 인덱스 의존성이 없다.
  - 아이템 코드를 키 기준으로 중복 없이 관리할 수 있다.
  - 인스턴스, UI, 메뉴가 동일 키로 같은 데이터 원본을 참조할 수 있다.

**추천 시각 자료**
- 아이템 클래스 계층 UML
- 오른쪽에 `DataTable 방식 vs Registry 방식` 비교 표

**발표 포인트**
- "이 슬라이드에서는 단순히 자료구조를 바꿨다는 게 아니라, 콘텐츠 관리 모델 자체를 바꿨다는 점을 강조하면 좋습니다."

## Page 5. ItemInstance 자동 적용 구조
**슬라이드 제목**
`키 기반 조회와 에디터 자동 반영`

**핵심 메시지**
- ItemInstance는 데이터를 직접 소유하지 않고, `ItemDataKey`를 통해 필요한 값을 해석해 자기 자신에 적용한다.

**본문 포인트**
- 구조
  - `AMHItemInstanceBase`가 `ItemRegistry`, `ItemDataKey`, `CachedItemData` 보유
  - `ApplyItemData()`를 가상 함수로 두고 하위 클래스가 오버라이드
- 자동 적용 방식
  - `BeginPlay()`에서 `ApplyItemData()`
  - `PostEditChangeProperty()`에서 값 변경 시 재적용
  - `#if WITH_EDITOR`로 에디터에서만 자동 반영
- 적용 예시
  - 무기 메시 적용
  - 롱소드 사야 메시 적용
- 의미
  - 대량의 아이템을 만들 때 수작업 세팅 비용을 줄인다.

**추천 시각 자료**
- `ApplyItemData()` 호출 흐름 다이어그램
- 코드 캡처 5~6줄: `PostEditChangeProperty()`와 `ApplyItemData()` 연결부

**발표 포인트**
- "런타임 비용은 억제하고, 에디터 생산성만 챙긴 설계라는 점을 함께 설명하면 프로그래머 관점이 더 잘 드러납니다."

## Page 6. 장비 스탯의 GAS 반영 구조
**슬라이드 제목**
`정적 ItemData를 전투용 Attribute로 변환`

**핵심 메시지**
- 인스턴스가 최종 스탯을 들고 있는 구조가 아니라, 장착 시점에 `GameplayEffect`로 변환해 ASC에 반영하는 구조다.

**본문 포인트**
- 장착 흐름
  - `SpawnAndEquipDefaultWeapon()`
  - `EquipWeaponInstance()`
  - `RefreshEquippedWeaponStatEffect()`
- 수치 반영 방식
  - `FMHAttackStats`에서 `AttackPower`, `Affinity` 추출
  - `UMHGameplayEffect_WeaponStat`에 `SetByCaller`로 주입
  - `UMHCombatAttributeSet`의 `AttackPower`, `CriticalRate`로 반영
- 예리도 처리
  - 정적 데이터: 분포와 최대 등급
  - 런타임 데이터: 현재값, 최대값, `SharpnessModifier`
- 장점
  - 인벤토리, 상점 UI, 장착 로직이 같은 데이터 키를 공유할 수 있다.

**추천 시각 자료**
- 장착 시퀀스 다이어그램
- `ItemData -> GE -> AttributeSet` 3단 박스 다이어그램

**발표 포인트**
- "무기 인스턴스가 스탯을 독점하지 않기 때문에, UI와 전투 로직이 같은 데이터 원본을 재사용할 수 있다는 점이 중요합니다."

## Page 7. 대미지 전달 파이프라인
**슬라이드 제목**
`공격 시작 시점의 수치를 Spec으로 스냅샷`

**핵심 메시지**
- 공격이 시작된 순간의 전투 상태를 `GameplayEffectSpec`에 담아 두고, 실제 명중 시점에는 그 스냅샷을 전달하는 구조다.

**본문 포인트**
- 흐름
  - Ability가 Source ASC에서 현재 수치 조회
  - 콤보/차지/상태 배율 계산
  - `DamageSpec` 생성
  - 무기 인스턴스에 전달
  - 히트박스 overlap 시 타깃에 전달
  - `ExecutionCalculation`에서 최종 대미지 계산
- 이 구조를 선택한 이유
  - 공격 시작 시점과 피격 시점을 분리할 수 있다.
  - 추후 투사체/지연 타격에도 같은 모델을 확장 가능하다.
  - 액션 연출과 수치 계산 책임을 분리할 수 있다.

**추천 시각 자료**
- `Docs/DamageDelivery_UML.md`의 플레이어 -> 몬스터 시퀀스 사용

**발표 포인트**
- "이 슬라이드는 포트폴리오에서 가장 강한 기술 포인트입니다. 단순 타격 판정이 아니라, 왜 스냅샷 구조가 필요한지까지 설명해야 합니다."

## Page 8. 피격 결과 처리와 후속 액션
**슬라이드 제목**
`성공/실패 분기와 Hit Acknowledge`

**핵심 메시지**
- 공격 성공 여부는 피격자가 판단하고, 공격자는 결과만 받아 후속 액션을 실행하는 구조로 결합도를 낮췄다.

**본문 포인트**
- 성공 시
  - Spec 적용
  - 대미지 계산 및 체력 반영
  - Attribute 변경을 통해 UI 갱신
  - VFX, SFX, 대미지 텍스트 처리
- 실패 시
  - 플레이어 콤보 초기화
  - 무기 콜리전 비활성화
  - 바운스/튕기기 몽타주 재생
- 설계 포인트
  - `IMHDamageSpecReceiverInterface`
  - `FMHHitAcknowledge`
  - 공격자와 피격자의 책임 분리

**추천 시각 자료**
- 성공/실패 분기 플로우차트
- `HitAcknowledge` 구조체 필드 간단 표

**발표 포인트**
- "무기가 타깃 타입을 몰라도 된다는 점, 그리고 결과 기반 후처리만 한다는 점이 설계적으로 깔끔하다고 설명하면 좋습니다."

## Page 9. 공통 UI 설계와 스탯 반영
**슬라이드 제목**
`UI는 표시만, 로직은 외부에서`

**핵심 메시지**
- UI 위젯은 게임 로직을 직접 가지지 않고, 외부에서 전달되는 값만 반영하는 방향으로 설계했다.

**본문 포인트**
- 공통 원칙
  - 위젯은 표시 전용
  - 로직은 캐릭터/ASC/상위 위젯이 담당
- 베이스 프로그레스 바
  - 단일 프로그레스 바
  - 스태미나/예리도 공용
  - `Max`, `Current`를 받아 퍼센트 계산
  - 상태에 따라 색상 변경 가능
- 레이어드 프로그레스 바
  - 두 개의 바를 겹친 구조
  - 디자인 편집성 때문에 공용 WBP 상속 대신 하드코딩 분리
- 실제 값 반영 흐름
  - 플레이어가 `GetGameplayAttributeValueChangeDelegate`에 UI 업데이트 함수 바인딩
  - 스탯 변화 시 즉시 반영

**추천 시각 자료**
- `기본 바 / 레이어드 바 / 실제 HUD 적용 화면` 3분할

**발표 포인트**
- "UI를 예쁘게 만들었다는 얘기보다, UI가 데이터를 어떻게 소비하는지 설명하는 쪽이 포트폴리오용으로 더 강합니다."

## Page 10. 대미지 텍스트 위젯/액터
**슬라이드 제목**
`월드 좌표 UI를 액터로 분리한 이유`

**핵심 메시지**
- 대미지 텍스트는 위젯과 액터를 분리해, 표시 책임과 월드 생명주기 책임을 나눴다.

**본문 포인트**
- 위젯 역할
  - 텍스트 출력
  - 애니메이션 보유 및 제공
- 액터 역할
  - 월드 특정 위치에 스폰
  - `WidgetComponent` 소유
  - 수명 관리
- 왜 별도 액터로 만들었는가
  - 몬스터/플레이어에 직접 어태치하지 않아도 된다.
  - 피격 대상이 UI 생명주기를 관리하지 않아도 된다.
  - 월드 위치 표시와 소멸 타이밍을 독립적으로 다룰 수 있다.

**추천 시각 자료**
- `Widget -> Actor -> World Spawn` 구조도
- 실제 대미지 텍스트 화면 캡처

**발표 포인트**
- "기능 구현보다 생명주기 분리 의도가 중요합니다. 특히 '피격자가 직접 UI를 오래 들고 있지 않도록 했다'는 설명이 좋습니다."

## Page 11. 메인 메뉴 구조
**슬라이드 제목**
`런타임 스폰 없이 CDO로 무기 프리뷰`

**핵심 메시지**
- 프론트 메인 메뉴는 실제 무기 액터를 만들지 않고, 무기 클래스 CDO와 데이터 키를 이용해 미리보기를 구성한다.

**본문 포인트**
- 무기 선택 슬롯
  - 무기 클래스 리스트를 기반으로 슬롯 동적 생성
  - 아이콘/이름/선택 상태 표시
- 선택 무기 스탯 패널
  - 선택된 무기 인스턴스의 데이터 키를 통해 값 조회
  - 공격력, 예리도, 회심, 속성 표시
- 구조적 장점
  - 메뉴 비용이 낮다.
  - 프론트와 전투 로직이 불필요하게 결합되지 않는다.
  - 같은 ItemData를 UI 프리뷰에도 재사용할 수 있다.

**추천 시각 자료**
- 메인 메뉴 화면
- `Weapon Class CDO -> ItemRegistry -> ItemData -> UI` 간단 흐름도

**발표 포인트**
- "이 부분은 Unreal의 CDO 개념을 실무적으로 활용했다는 점에서 포트폴리오 어필 포인트가 됩니다."

---

## Page 12. 로딩 화면과 레벨 전환
**슬라이드 제목**
`Controller가 지휘하고 GameInstance가 상태를 유지`

**핵심 메시지**
- 버튼은 이벤트만 발생시키고, 실제 전환은 PlayerController가 지휘하며, 레벨 간 유지 상태는 GameInstance가 들고 가는 구조로 분리했다.

**본문 포인트**
- 책임 분리
  - 메인 메뉴 버튼: 시작 요청만 전달
  - `FrontendPlayerController`: 화면 전환과 로딩 표시 지휘
  - `FrontendGameInstance`: `PendingWeaponClass`, 목적지 레벨, 로딩 진행 상태 관리
  - `PlayerCharacter`: 전투 시작 시 선택 무기 소비
- 로딩 화면 방식
  - 실제 로딩 관리는 `GameInstance`
  - 로딩 위젯은 매 틱 폴링으로 진행률/문구 반영
- 장점
  - UI와 레벨 전환 정책이 분리된다.
  - 선택 무기가 레벨 변경 후에도 유지된다.

**추천 시각 자료**
- `메뉴 -> 로딩 -> 전투 레벨` 시퀀스 다이어그램

**발표 포인트**
- "UI는 요청만 하고, 상태와 전환은 세션 레이어가 담당한다는 구조를 강조하면 설계 의도가 잘 보입니다."

## Page 13. 설계 강점
**슬라이드 제목**
`이 프로젝트에서 보여줄 수 있는 엔지니어링 포인트`

**핵심 메시지**
- 구현 결과보다, 어떤 기준으로 책임을 나누고 확장성을 확보했는지가 이 프로젝트의 강점이다.

**본문 포인트**
- 데이터 정의와 런타임 적용의 분리
- 액션 로직과 수치 계산의 분리
- 프론트 UI와 인게임 UI의 참조 경로 분리
- 에디터 자동 적용을 통한 콘텐츠 제작 편의성 확보
- GAS를 전면 도입하지 않고, 필요한 부분에만 사용하는 하이브리드 설계

**추천 시각 자료**
- 5개 키워드 카드
  - `Data Driven`
  - `Responsibility Split`
  - `GAS Hybrid`
  - `Editor Productivity`
  - `UI Sync`

**발표 포인트**
- "면접관이나 리뷰어가 듣고 싶은 건 '무엇을 만들었나'보다 '왜 그렇게 나눴나'인 경우가 많아서, 이 슬라이드가 중요합니다."

## Page 14. 한계와 개선안
**슬라이드 제목**
`잘 된 점보다, 어디를 더 고치고 싶은가`

**핵심 메시지**
- 스스로 구조의 한계를 인지하고 다음 개선 방향까지 설명해야 포트폴리오 설득력이 올라간다.

**본문 포인트**
- 현재 한계
  - VFX/SFX/대미지 텍스트 스폰 책임이 피격자 쪽에 몰려 있음
  - 레이어드 프로그레스 바는 중복 로직이 생기기 쉬움
  - `ApplyItemData()`는 비주얼 중심이라 런타임 재적용 범위가 제한적
  - `GetItemData()`와 직접 `Find()`가 혼재
  - 인벤토리 실물 인스턴스, 채집/루팅은 미구현
- 개선 방향
  - 피드백 시스템을 `Subsystem`으로 분리
  - 풀링 시스템 도입
  - `EquipmentApplier` 성격의 장착 반영 모듈 분리
  - 공용 helper 기반 UI 로직 통합
  - 런타임 refresh API 정리

**추천 시각 자료**
- `Current -> Better` 비교표

**발표 포인트**
- "반성 포인트를 기능 미완성 수준으로만 말하지 말고, 구조적으로 왜 아쉬운지를 설명해야 합니다."

## PPT 제작 팁
- 한 페이지에는 한 메시지만 두는 편이 좋다.
- UML은 원본을 그대로 많이 넣기보다, 발표용으로 핵심 노드만 남긴 축약 버전을 쓰는 것이 좋다.
- 코드 캡처는 최대 6~8줄 정도로 제한하고, 함수 전체보다 `의도가 드러나는 부분`만 잘라 넣는 것이 좋다.
- 회고 슬라이드는 반드시 넣는 편이 좋다. 구현 능력보다 설계 판단력이 더 잘 드러난다.
