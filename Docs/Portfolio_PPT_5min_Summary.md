## 1. 아이템 데이터 레지스트리

### 핵심 메시지
- 서로 다른 프로퍼티를 가진 아이템들을 하나의 통합 DataTable로 억지로 관리하지 않고, `계층형 ItemData + Registry` 구조로 분리해 관리했다.

### 왜 이렇게 설계했는가
- 무기, 방어구, 소비 아이템은 필요한 데이터가 다르다.
- 하나의 통합 스키마로 관리하면 불필요한 프로퍼티가 계속 늘어나고, 유지보수가 어려워진다.
- 그래서 각 아이템 데이터는 계층 구조로 필요한 데이터만 소유하고, 외부에서는 `KeyName`으로 동일한 방식으로 조회하도록 설계했다.
- 대량의 데이터를 한 곳에서 관리하는 데이터 테이블의 장점은 유지하려고 했다. 

### 어떻게 동작하는가
- `UItemDataRegistry`가 `FName Key` 기반으로 아이템 데이터를 통합 관리한다.
- 외부 시스템은 아이템 데이터를 직접 들고 있지 않고, `KeyName`으로 조회한다.
- 이 레지스트리는 사실상 `데이터 에셋 매니저` 역할을 한다.

### 실제 사용 예시
- 장비 장착 시:
  - 무기 인스턴스가 가진 `KeyName`으로 스탯 데이터를 조회
  - 조회한 값을 기반으로 `GameplayEffect`를 생성하고 ASC에 적용
- 메인 메뉴:
  - 선택한 무기 클래스의 `KeyName`으로 스탯 패널 데이터를 조회
- 확장성:
  - 인벤토리, 상점, 아이콘, 아이템 설명 등도 같은 레지스트리에서 조회 가능
  - 대량의 아이템을 생성, 관리 비용이 매우 줄어들음

### 아이템 인스턴스 설계
- 아이템 인스턴스는 모든 데이터를 들고 있지 않고, 자신에게 필요한 최소 데이터만 적용한다.
- 외부에서 데이터가 필요할 때는 인스턴스가 `KeyName`을 제공한다.
- `KeyName`이 적용되면 자동으로 데이터가 반영되도록 자동화했다.
  - 베이스 클래스의 가상 함수 기반으로 구성
  - 파생 클래스가 필요한 방식으로 자동 적용 로직을 오버라이드 가능

### 이 파트에서 강조할 점
- 핵심은 `데이터 정의`와 `런타임 적용`을 분리한 것이다.
- 아이템 데이터는 콘텐츠 원본이고, 인스턴스는 그 데이터를 해석해 적용하는 역할만 가진다.

## 2. 대미지 시스템

### 핵심 메시지
- GAS를 사용해 전투 수치를 처리하되, 액션 로직 전체를 GAS에 넣지 않고 `공격 생성`, `피격 판정`, `최종 계산`을 나눠 설계했다.

### 왜 이렇게 설계했는가
- 액션 게임은 공격 시작 시점과 실제 명중 시점이 다를 수 있다.
- 그래서 공격 시점에 `DamageSpec`을 생성해 두고, 그 순간의 버프와 장비 상태를 고정해서 전달하도록 만들었다.
- 이 구조는 근접 공격에는 다소 적합하지 않을 수 있지만 추후 투사체 공격을 고려해 설계했다.

### 대미지 전달 흐름
- 공격 Ability가 현재 ASC 상태를 읽어 공격용 `Spec` 생성
- 생성한 Spec을 무기 인스턴스에 전달
- 히트박스 충돌 시 타깃에게 전달
- 타깃은 피격 가능 여부를 판단
- 성공하면 `ExecutionCalculation`이 최종 대미지 계산
- `AttributeSet`이 실제 체력 변화 반영

### 역할 분리
- 타격자:
  - 공격 시점의 상태를 기반으로 공격 의도를 만든다.
- 피격자:
  - 맞을 수 있는지 판단하고, 피격 후처리를 담당한다.
- Calculation / Execution:
  - 공격자가 만든 기본 대미지와
  - 피격자의 방어력, 내성, 상태를 조합해 최종 대미지를 계산한다.

### UI와 피드백 연결
- `AttributeSet` 값 변경은 델리게이트로 UI에 전달된다.
- 피격 위치에는 다음 피드백을 스폰한다.
  - VFX
  - SFX
  - 대미지 텍스트 위젯

### 이 파트에서 강조할 점
- 핵심은 `공격 연출`과 `수치 계산`을 분리한 것이다.
- GAS는 전투 수치 실행 백엔드로 사용하고, 액션 제어는 코드에서 직접 다루는 하이브리드 구조다.

## 3. UI

### 핵심 메시지
- UI는 값을 보여주는 `뷰어` 역할만 담당하고, 값과 로직은 소유하지 않도록 설계했다.

### 설계 원칙
- UI는 상태를 계산하지 않는다.
- UI는 외부에서 전달받은 값을 표시만 한다. (체력, 스태미나, 예리도, 기인게이지의 최대/현재 값. 예리도 단계 색상, 기인게이지 단계 색상)
- 실제 로직은 캐릭터, ASC, 상위 위젯, 컨트롤러가 담당한다.

### 실제 적용 방식
- 인게임 UI:
  - 플레이어가 Attribute 변화 델리게이트를 받아 UI 업데이트 함수에 전달
  - UI는 전달받은 값으로 체력, 스태미나, 예리도만 반영
- 메인 메뉴 UI:
  - 선택한 무기의 `KeyName`으로 레지스트리 데이터를 조회
  - 스탯 패널과 슬롯 UI는 조회 결과를 표시만 함

### 이 설계의 장점
- UI와 게임플레이 로직이 강하게 결합되지 않는다.
- 데이터 흐름을 추적하기 쉽다.
- 메뉴 UI와 인게임 UI가 서로 다른 상황에서도 같은 데이터 원본을 재사용할 수 있다.

### 이 파트에서 강조할 점
- UI를 예쁘게 만드는 것보다, `UI가 어떤 데이터를 어떤 경로로 소비하는가`가 더 중요한 설계 포인트였다.

## 4. 한계와 개선안

### 핵심 메시지
- 현재 구조는 확장 가능한 방향으로 설계했지만, 실제 프로젝트 기준으로는 책임이 일부 몰려 있는 지점과 재사용성이 아쉬운 부분이 있다.

### 한계
- 아이템 데이터 레지스트리
  - 전역 접근을 위한 아이템 데이터 서브시스템이 구축하지 못했다. 현재는 각 사용자가 레지스트리를 직접 참조하는 방식이다
- 대미지 시스템
  - VFX, SFX, 대미지 텍스트 생성 책임이 피격자 쪽에 모여 있어 역할 분리가 덜 되어 있다.
  - 현재 구조는 잘 동작하지만, 피드백 시스템이 커질수록 관리 포인트가 늘어날 수 있다.

### 개선안
- 아이템 데이터 레지스트리
  - 레지스트리 조회 API를 Subsystem 하나로 통일해 참조 경로를 단순화
- 대미지 시스템
  - VFX, SFX, 대미지 텍스트를 `Subsystem`으로 분리해 피격자 책임 축소
  - 대미지 텍스트와 피드백은 풀링 시스템까지 고려해 최적화 가능

### 이 파트에서 강조할 점
- 이 프로젝트는 완성된 결과물도 중요하지만, 어디를 더 구조적으로 개선할 수 있는지 스스로 판단했다는 점이 더 중요하다.
