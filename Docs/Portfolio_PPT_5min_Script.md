`왜 이 구조로 설계했는가`

### 목표 시간
`25초`

### 발표 대본
시스템 및 UI 파트에서 가장 먼저 정한 기준은 구현을 맡은 파트의 각 레이어 책임을 분리하는 것이었습니다.  
`ItemData`는 콘텐츠 원본만 정의하고, `ItemInstance`는 그 데이터를 런타임에서 해석해 적용합니다.  
실제 장비 수치와 전투 계산은 `Player`와 `GAS`가 담당하고, `UI`는 최종 결과만 표시하도록 나눴습니다.  
이 기준 덕분에 데이터, 전투, 화면 표시를 각각 독립적으로 관리할 수 있었습니다.

### 연결 멘트

## Page 3

### 슬라이드 제목
`아이템 데이터 레지스트리`

### 목표 시간
`70초`

### 발표 대본
아이템 파트에서 먼저 해결하려던 문제는, 서로 다른 아이템을 하나의 통합 DataTable로 관리할 때 생기는 스키마 비대화였습니다.  
무기, 방어구, 소비 아이템은 필요한 프로퍼티가 다르기 때문에, 하나의 구조로 억지로 묶으면 불필요한 데이터와 예외 처리가 계속 늘어납니다.  
그래서 저는 `계층형 ItemData`와 `KeyName 기반 Registry` 구조를 선택했습니다.  

각 아이템 데이터는 계층 구조로 필요한 데이터만 가지고, 외부 시스템은 `FName Key`로만 접근합니다.  
즉, `UItemDataRegistry`가 사실상 데이터 에셋 매니저처럼 동작하는 구조입니다.  

이 방식의 장점은 같은 데이터를 여러 시스템이 같은 방식으로 재사용할 수 있다는 점입니다.  
장비 장착 시에는 무기 인스턴스의 `KeyName`으로 스탯을 조회해서 `GameplayEffect`를 만들고, 메인 메뉴에서는 같은 `KeyName`으로 스탯 패널을 구성할 수 있습니다.  
또 추후 인벤토리나 상점으로 확장하더라도, 아이콘이나 설명을 같은 레지스트리에서 조회할 수 있습니다.  

그리고 `ItemInstance`는 모든 데이터를 복사해서 들고 있지 않고, 자신에게 필요한 최소 정보만 적용합니다.  
`ApplyItemData()`를 가상 함수로 두어서, 파생 클래스가 필요한 방식으로 자동 적용 로직을 오버라이드할 수 있게 만들었습니다.

### 연결 멘트
정리하면 이 파트의 핵심은, 데이터 정의와 런타임 적용을 분리했다는 점입니다.  
다음은 이 데이터가 실제 전투 수치로 어떻게 이어지는지 설명드리겠습니다.

## Page 4

### 슬라이드 제목
`대미지 시스템`

### 목표 시간
`80초`

### 발표 대본
대미지 시스템은 `GAS`를 전투 수치 백엔드로 사용하는 방향으로 설계했습니다.  
다만 액션 게임에서는 공격 시작 시점과 실제 명중 시점이 다를 수 있기 때문에, 공격 로직 전체를 GAS에 맡기지는 않았습니다.  

핵심은 `공격 시점에 DamageSpec을 먼저 만든다`는 점입니다.  
Ability가 현재 ASC 상태를 읽고, 그 순간의 버프와 장비 수치를 반영한 공격 Spec을 생성합니다.  
그다음 무기 인스턴스가 이 Spec을 보관하고 있다가, 히트박스 충돌 시 타깃에게 전달합니다.  

이후 피격자는 먼저 맞을 수 있는지 판단합니다.  
수락된 공격만 `ExecutionCalculation`이 방어력, 내성, 크리티컬 같은 요소를 반영해서 최종 대미지를 계산하고, `AttributeSet`이 그 결과를 실제 HP 변화로 적용합니다.  

즉, 역할을 나누면 이렇습니다.  
타격자는 공격 의도를 만들고, 피격자는 수락 여부와 후처리를 담당하고, GAS는 최종 수치 계산과 체력 반영을 담당합니다.  

이 구조를 선택한 이유는, 공격 시작 순간의 상태를 그대로 유지할 수 있고, 이후 투사체처럼 공격 생성 시점과 명중 시점이 더 벌어지는 구조에도 확장하기 쉽기 때문입니다.  
또 Attribute 변경은 델리게이트로 UI에 전달하고, 피격 위치에는 VFX, SFX, 대미지 텍스트를 연결해서 전투 피드백까지 이어지게 했습니다.

### 연결 멘트
여기서 중요한 점은 UI도 이 수치를 직접 계산하지 않는다는 것입니다.  
그래서 다음으로 UI 구조를 보겠습니다.

## Page 5

### 슬라이드 제목
`UI는 Viewer 역할만 담당`

### 목표 시간
`50초`

### 발표 대본
UI는 값을 보여주는 `Viewer` 역할만 담당하도록 설계했습니다.  
UI가 직접 상태를 계산하거나 소유하기 시작하면, 게임플레이 로직과 강하게 결합되기 때문입니다.  

인게임 UI에서는 `PlayerCharacter`가 Attribute 변경 델리게이트를 받아서 위젯으로 전달하고, 위젯은 체력, 스태미나, 예리도 같은 값을 표시만 합니다.  
메인 메뉴 UI도 같은 원칙을 따릅니다. 선택한 무기의 `KeyName`으로 레지스트리 데이터를 조회하고, 슬롯과 스탯 패널은 조회 결과를 표시만 합니다.  

결국 UI는 상태 저장소가 아니라, 외부 시스템이 정리해 준 값을 소비하는 최종 표시 레이어라고 정리할 수 있습니다.  
이 구조 덕분에 UI와 게임플레이 로직의 결합도를 낮추고, 데이터 흐름도 더 쉽게 추적할 수 있었습니다.

### 연결 멘트
마지막으로, 이 구조를 적용하면서 느꼈던 한계와 다음 개선 방향을 짧게 말씀드리겠습니다.
