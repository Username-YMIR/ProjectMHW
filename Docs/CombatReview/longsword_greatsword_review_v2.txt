[버전 2] 설계 정합성 관점 상세 분석
기준: Source.zip(태도) + Source.05 snapshot 정리(대검)
작성일: 2026-03-23

A. 태도(LS)
A-1) 입력-그래프-자원의 3축은 구조적으로 좋다
- 입력 해석(플레이어) / 분기(ComboGraph) / 실행(GA) / 자원(플레이어) 분리는 유지보수 친화적.
- Notify 기반 체인/조기전환/카운터 창 분리도 방향성은 적절.

A-2) 정합성 깨지는 지점
(1) 그래프 선언 중복
- FadeSlash 노드의 ForesightSlash 브랜치 중복.
- 문서와 코드 1:1 추적 시 혼란.

(2) 데이터 누락 내성의 방향이 반대
- AttackMeta 미존재를 permissive(true)로 둔 것은 데이터 기반 전투에서 위험.
- 누락은 fail-fast(기술 불가 + 경고 로그)가 맞다.

(3) 실패 경로 상태정리 편차
- 정상 종료/인터럽트는 큰 틀에서 정리되는데,
  ActivateAbility 진입 실패 분기에서 플래그 정리가 축소되어 있음.

A-3) 권장 설계 원칙
- 원칙 1: "데이터 누락은 허용하지 않는다" (fail-fast)
- 원칙 2: "종료 경로는 어떤 경로든 동일 상태로 수렴"
- 원칙 3: "그래프 선언은 중복 0건"

B. 대검(GS)
B-1) 상태기계 접근 자체는 무기 특성과 잘 맞음
- 차징/태클 family 보존, 유틸리티/공격 분리, notify 창 기반 분기는 대검에 적합.

B-2) 정합성 리스크
(1) 가드 해제 타이밍
- 입력 release 시점과 실제 guard_end 모션 종료 시점이 분리되어 있어,
  state(Acting)와 animation(guard_end 재생 중) 미스매치 가능.

(2) 유틸리티 재생 실패 복구
- 실패 시 상태 롤백이 보장되지 않으면, 입력 무응답/고착 형태의 간헐 버그 유발.

B-3) 권장 설계 원칙
- 원칙 1: "상태 전환의 단일 진실원천은 몽타주 종료 이벤트"
- 원칙 2: "재생 실패는 항상 안정상태(Neutral)로 복귀"

C. 공통 개선 체크리스트
- [ ] 실패 경로 공통 정리 함수 도입
- [ ] 데이터 누락 fail-fast 로깅(태그/row명/무기타입)
- [ ] 입력창/전환창 진입/종료 로그 레벨 표준화
- [ ] QA 재현 시나리오 자동 체크(최소 smoke)
